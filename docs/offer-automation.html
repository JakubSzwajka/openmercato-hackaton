Offer automation: inbound email to draft quote
offer_automation · hackathon build · Open Mercato core 0.8.0

An email becomes a draft quote with no retyping, behind one human gate

A customer asks for an offer by email. Two event subscribers race for it, ours wins, and a model reads it into a proposal. App-owned code executes that proposal as a machine account holding exactly one feature, and creates a sales quote priced from the catalog by a function the model cannot reach. A notification tells the sales desk. The only gate is a person reviewing the draft quote before sending it. Seven runs on one email body, 14 of 14 line items correct, 589 EUR every time. That proves the mechanism. It does not prove the model generalises to arbitrary freight enquiries. The orange parts are the shims where core assumes a browser, and two upstream bugs neither of which is posted.

part 1 · the domain

Four nouns in freight, and we touch two

Selling transport runs through four records, in order. This build starts at the first and stops at the second.

Freight does not behave like selling boxes. There is no stock to draw down, the unit sold is a service, and the price follows a lane, one origin to one destination, rather than an item. A catalog price gets you a demo. A rate card gets you a product.

What real lane pricing needs planned

This build prices from four flat catalog rows, and section 13 shows the arithmetic. Charging for a real lane needs three things this app does not have. A routing source for road kilometres between two addresses. A rate model shaped base + per_km + per_pallet + accessorials + fuel surcharge. And the truck realities a demo can ignore: vehicle type, ADR for dangerous goods, ferry legs, tolls, and cabotage rules on who may drive a leg. None of that fits in a catalog price row, so a rate card would be the first thing here to need its own entity and its own migration.

part 1 · the business feature

One email, one decision, zero retyping

Everything between the email arriving and the draft quote appearing is automatic. One person reviews it before the customer hears anything.

Before: two human gates
  • A person accepted the extracted action in Inbox Ops.
  • A person reviewed the draft quote in Sales.
  • Two clicks before the customer heard anything.
Now: one human gate
  • The executor subscriber runs the action on its own.
  • A salesperson reviews the draft quote in Sales.
  • One click. The quote is the review artefact, not the JSON payload.

part 2 · how it is built

Two subscribers race for one email

Core's extraction worker listens to the same event as ours. The event bus runs persistent subscribers concurrently (Promise.allSettled, @open-mercato/events/src/bus.ts:369). Disabling core's worker would mean editing src/modules.ts, which was off-limits. So our subscriber claims the email atomically: if it wins it extracts; if core wins first it waits for core's verdict and takes the email over from failed; if core's extraction is ever fixed upstream it sees processed and stands down.

Why not disable core's worker

The module list in src/modules.ts is the contract surface. Removing inbox_ops from it would break every installed feature that depends on it. There is no per-subscriber toggle. So the two run, and our subscriber handles the race.

part 2 · how it is built

The machine account holds one feature

automation@nordwind-logistics.example is a real user account. It is not is_super_admin. It holds exactly one feature, offer_automation.offers.draft, scoped to one organization. The RBAC gate at executionEngine.ts:474 still runs, so the automation has an identity rather than a bypass.

part 2 · how it is built

Money enters in one function, and the model never sees it

The quote arrives priced, so the salesperson reviews rather than retypes. We own no entity and no migration: the executor maps the payload onto a command input and calls sales.quotes.create, which keeps its validation, numbering, locking, audit entry and events.

The extraction schema (lib/freightExtraction.ts:86-100) has no field for an amount anywhere. A model on this path cannot even return a price, let alone set one.

A catalog price is one number, real freight pricing is not

Freight is priced by lane, origin to destination, with weight bands and surcharges. A catalog variant carries one price. This build models the simple version on purpose, so the lane-based model is the next thing to design rather than something the code half-does today.

Four shims and two upstream bugs

Four files work around core assumptions, and two upstream bugs are confirmed by probing but not posted.

ShimWorks aroundNeeded byDeleted when

demoMessageRecord.ts The message-object registry is filled only by src/bootstrap-common.ts:37, and core/modules/inbox_ops/message-objects.ts:2 statically imports a React preview, so the generated registry cannot load in plain Node. the demo CLI Core loads message objects in its CLI bootstrap, or splits that preview out.
Upstream bug 1: third-party action types 403 before RBAC

REQUIRED_FEATURES_MAP in inbox_ops/lib/constants.ts:12 is a closed 9-entry map. An unknown actionType returns undefined at executionEngine.ts:454, and :456 throws 403 before the definition's own requiredFeature is ever read. Super-admin does not bypass it. We shim the key at boot (coreRequiredFeatureShim.ts); the RBAC check at :474 still runs against the feature we declared. Confirmed by probe, not posted.

Upstream bug 2: core's AI extraction fails on every email on an OpenAI install

extractionOutputSchema at inbox_ops/data/validators.ts:218 uses .optional() on several properties (:14-22, :25, :27-28, :33-34). OpenAI strict structured outputs rejects any schema whose properties are not all listed as required. Probed: .nullable() passes, .optional() fails, structuredOutputs: false does not help. This is why we run our own extraction (lib/freightExtraction.ts). Confirmed by probe, not posted.

part 3 · how to test it

The runbook: seed, send, watch, check

Log in as sales@nordwind-logistics.example in tenant Nordwind Logistics. An empty /backend/messages usually means the wrong tenant is selected in the tenant picker.

  1. Seed the demo once. Creates the tenant, users, catalogue, CRM companies, and the automation account. Idempotent.
    seed-demo
    yarn mercato offer_automation seed-demo
  2. Send an email with no arguments. Creates one email, emits the event, and watches. The extraction subscriber calls the model, the executor drafts the quote, and a notification arrives.
    send-email, zero arguments
    yarn mercato offer_automation send-email
  3. Send a custom email. The sender address, subject, and body are all overridable. Use --help for the full flag list.
    custom body from a file
    yarn mercato offer_automation send-email \
  --body-file ./my-enquiry.txt
  4. Force a refusal. Ask for a currency the catalogue has no price in. The action ends failed, no quote is created, and an error notification goes to the desk.
    the USD refusal
    yarn mercato offer_automation send-email \
  --note "Please quote in USD."
  5. Check the trail. Lists recent draft_offer actions, their proposals, and which quote each one produced.
    origins
    yarn mercato offer_automation origins
The queue worker must be running

yarn dev auto-spawns it (AUTO_SPAWN_WORKERS=true, .env:239). If send-email reports nothing reacted, check that the worker process is alive. A bare event hop takes about 0.8s. The 20s wall clock is two model calls: core's doomed one plus ours.

part 3 · limits

One email body, seven times

The reliability number rests on one email body, run seven times, against a four-item catalogue. It proves the mechanism. It does not prove the model generalises to arbitrary freight enquiries.

Extraction is narrow on purpose. lib/freightExtraction.ts proposes exactly one action type (draft_offer), does not classify categories, does not draft replies, does not record discrepancies and does not match contacts. Core's worker still owns all of that the moment it can run again. The day core's extraction schema becomes strict-safe, the subscriber quietly stops doing any work (outcome 3 in section 06).

part 3 · limits

The seeder refuses a production database

assertDisposableSeedTarget (lib/demoCompany.ts:102) runs before any write. When NODE_ENV is production, the only override is one exact environment variable with one exact value. Truthy values such as true or 1 do nothing.

Price seeding takes an advisory lock

ensureListPrice (lib/freightCatalog.ts:292) runs in em.transactional with pg_advisory_xact_lock (:308), re-reads inside the lock, then creates if the row is still missing. CatalogProductPrice has no unique constraint on (variant, currency, kind, minQuantity, channel) while SKUs do. What remains racy: any writer that does not take the same lock, such as the backend price editor.
